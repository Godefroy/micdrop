# Show Voice Agent Tool Calls in the Browser

When a Micdrop voice agent runs a tool on your Node server, the browser learns about it through two channels. Every call and its result appear in `Micdrop.conversation` as `tool_call` and `tool_result` items, whatever the tool. Tools declared with `emitOutput: true` also fire a `ToolCall` event carrying the parsed parameters and output, which is the channel to use when the result changes what the screen shows, such as a booking card. The tool itself runs on the server, where you [declare it with `addTool()`](../server/tools), so the browser only displays what happens.

## What reaches the browser during a tool call

1. The model asks for a tool. The server adds a `tool_call` item to the conversation and sends it to the client before running `execute`.
2. `execute` runs on the server. The client receives nothing in the meantime.
3. The `tool_result` item arrives with the output as a JSON string.
4. When the tool has `emitOutput: true`, the `ToolCall` event follows right after with the same output, already parsed.
5. The assistant speaks its answer, unless the tool has `skipAnswer`.

A `tool_call` waiting for its `tool_result` means the tool is still running, so it is your signal for a loading state. The `ToolCall` event comes after `execute` has returned, too late for a spinner.

|                       | Conversation items                                               | `ToolCall` event                                     |
| --------------------- | ---------------------------------------------------------------- | ---------------------------------------------------- |
| Sent for              | Every tool the agent runs, the built-in ones included            | Tools declared with `emitOutput: true`               |
| Arrives               | `tool_call` before `execute`, `tool_result` after                | Once, right after `tool_result`                      |
| Parameters and output | JSON strings to pass through `JSON.parse`                        | Parsed values                                        |
| Links call and result | `toolCallId` on both items                                       | One event holds both                                 |
| Available             | In `Micdrop.conversation` until the next `Micdrop.start()`       | To the listeners subscribed when it fires            |
| Read with             | `Micdrop.conversation`, the `Message` event, `useMicdropState()` | `Micdrop.on('ToolCall')`, `useMicdropToolCall()`     |

The built-in tools appear in the conversation too, under the names `end_call`, `semantic_turn` and `ignore_user_noise` when you turn on `autoEndCall`, `autoSemanticTurn` or `autoIgnoreUserNoise`. Filter them out before you [display the conversation](./display-conversation-messages).

The same flow holds with a speech to speech model such as the OpenAI Realtime API or Gemini Live, because a [realtime model](../realtime) runs its tools through the same agent code.

## Show a loading state while a tool runs

Listen to the `Message` event, which fires for each item added to the conversation, and track the calls by `toolCallId`:

```typescript
import { Micdrop, MicdropConversationItem } from '@micdrop/web'

const running = new Map<string, string>() // toolCallId → toolName

Micdrop.on('Message', (item: MicdropConversationItem) => {
  if (item.role === 'tool_call') {
    running.set(item.toolCallId, item.toolName)
  } else if (item.role === 'tool_result') {
    running.delete(item.toolCallId)
  } else if (item.role === 'assistant') {
    // The answer that follows a failed tool
    running.clear()
  }
  showRunningTools([...running.values()])
})
```

When `execute` throws, the server sends the error to the model and the client gets no `tool_result` for that call. The model then answers, usually to say the action failed, so clear the pending calls when that `assistant` message arrives. With `OpenaiAgent`, the model can also write a sentence along with its tool call. That `assistant` message reaches the conversation before the `tool_call` item, so the handler clears `running` before it adds the new call.

When the user interrupts the assistant, a tool already running still finishes and its `tool_result` still arrives.

## Update the interface with the tool output

Return from `execute` the data your interface needs, and set `emitOutput` on the tool:

```typescript
// Server
agent.addTool({
  name: 'book_meeting',
  description: 'Book a meeting in the calendar of the user',
  inputSchema: z.object({ date: z.string(), time: z.string() }),
  execute: async ({ date, time }) => {
    const meeting = await bookMeeting(date, time)
    return { id: meeting.id, date, time }
  },
  emitOutput: true,
})
```

```typescript
// Browser
import { Micdrop, MicdropToolCall } from '@micdrop/web'

Micdrop.on('ToolCall', (toolCall: MicdropToolCall) => {
  if (toolCall.name === 'book_meeting') {
    showBookingCard(toolCall.output)
  }
})
```

The event has three fields:

```typescript
interface MicdropToolCall {
  name: string // Name of the tool
  parameters: any // Arguments the model passed, parsed
  output: any // Value returned by execute
}
```

The output travels over the WebSocket as JSON. A `Date` arrives as a string and a class instance as a plain object, so return plain data. The same value goes to the model and, inside the `tool_result` item, to the browser for every tool, `emitOutput` or not. Anyone with the developer tools open can read it, so keep tokens, internal ids and other users' data out of what `execute` returns.

To act on the parameters alone, read the `tool_call` item, which arrives before `execute` runs, for every tool.

## Handle tool calls in React

The `useMicdropToolCall` hook of [`@micdrop/react`](./react-hooks) subscribes to the `ToolCall` event and unsubscribes when the component unmounts. Wrap the callback in `useCallback`, since the hook subscribes again each time the function changes:

```tsx
import { useMicdropToolCall } from '@micdrop/react'
import { MicdropToolCall } from '@micdrop/web'
import { useCallback, useState } from 'react'

type Booking = { id: string; date: string; time: string }

function BookingCard() {
  const [booking, setBooking] = useState<Booking | null>(null)

  const handleToolCall = useCallback((toolCall: MicdropToolCall) => {
    if (toolCall.name === 'book_meeting') setBooking(toolCall.output)
  }, [])
  useMicdropToolCall(handleToolCall)

  if (!booking) return null
  return (
    <p>
      Meeting booked on {booking.date} at {booking.time}
    </p>
  )
}
```

`useMicdropState()` returns the conversation with its tool items, for a component that lists them. In React Native, import `Micdrop` and the types from `@micdrop/react-native`. The hooks stay the same.

## Approve an action before it runs

Tool calls travel one way, from the server to the browser. To have the user confirm an action, ask the model in the system prompt to read the details back and wait for a yes before calling the tool. The user then confirms by voice, so the `tool_call` item reaches the browser only once they have agreed.
